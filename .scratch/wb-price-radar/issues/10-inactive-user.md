# 10: Неактивный пользователь: деактивация при UserBlocked, реактивация на /start

**What to build:** Если пользователь заблокировал бота, любой `send` (Уведомление из воркера или ответ bot-хендлера) получает `UserBlocked` — и вызывающий через `Store.deactivate_user` помечает пользователя и все его Отслеживания неактивными, ничего не удаляя (CONTEXT: Неактивный пользователь). С этого момента Цикл проверки их больше не спрашивает (`tracked_nms`/`active_dests` их не видят). После разблокировки пользователь пишет `/start` → `reactivate_user` возвращает прежние Отслеживания с прежними Ценами сравнения — перенастраивать список не нужно. Spec, пользовательские истории 33–34.

**Blocked by:** 05 (бот: /start-ответ тоже ловит UserBlocked), 08 (воркер: путь commit/deactivate в Цикле)

**Status:** accepted

- [ ] `UserBlocked` от любого send (worker и bot) → ровно один `Store.deactivate_user` на событие; проверка «ровно один» не зависит от числа Уведомлений в пачке
- [ ] Неактивный пользователь: `active_dests`/`tracked_nms` его Отслеживаний не отдают; `list_trackings`/`find_tracking` удалённых строк не показывают — строк нет в удалении, статусы активны/неактивны
- [ ] `/start` после разблокировки → `reactivate_user`: статусы восстановлены, Цены сравнения прежнее (не пересчитывается)
- [ ] Уведомления о Недоступности для неактивного пользователя не копятся в обход деактивации (commit флага не происходит без доставки)
- [ ] Тесты на fake-швах: ровно один `deactivate_user` на событие; реактивация восстанавливает статусы и сохраняет Цены сравнения (spec, «Решения по тестированию» п.5–6)
- [ ] E2E-сценарий: блокировка → следующий Цикл молчит и не опрашивает его dest (если других нет) → `/start` → Цикл снова шлёт Уведомления (spec, п.6)
